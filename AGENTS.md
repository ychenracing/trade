# Repository working agreement

## Scope and working method

Follow the current task's explicit scope and acceptance criteria within platform permissions. Preserve business, security, data, economic and release contracts. Read applicable nested `AGENTS.md` before editing that directory; historical plans are context, not new authority. Analysis-only and approval-before-edit requests remain read-only until authorized.

Resolve mutable branch, SHA, PR and check facts from GitHub and inspect existing local changes. Resume matching work. Read only the relevant project brief, recovery state, diff and affected files; expand for uncertainty or impact and reuse unchanged context. Skills are optional methods unless the platform requires their use, not additional authorization, approval or stopping gates. For bounded authorized work, do not impose repeated design confirmations, mandatory full workflows or ceremonial announcements.

Prefer the smallest sufficient change, existing implementation and dependencies. Plan material decisions, not duplicate implementation. Batch related edits; parallelize only independent work with one writer per shared file, branch, runtime or evidence identity.

## Testing and verification

- Use risk-based, minimum sufficient verification based on changed behavior and real call paths. Explicitly do not enforce Superpowers TDD or fresh-verification-per-message workflows. Tests may precede or follow implementation; never delete working code solely because it was written before a test. For a defect, prefer a minimal reproduction and a regression test when needed; reuse existing coverage and avoid redundant or brittle implementation-detail tests.
- During development, run the failing case and directly affected checks, then expand for concrete cross-module risk, uncertain impact or an explicit applicable acceptance requirement. Batch related fixes. Neither every small edit nor every final delivery automatically requires the full suite, all tools or a complete backtest matrix.
- Reuse results while covered code/behavior, tests, dependencies, configuration, data and relevant environment remain equivalent. Only affected evidence is invalidated. A message, handoff, commit, push or new SHA alone does not require rerunning unchanged checks. Record the actual tested source and reuse scope; never present an old CI result as a new HEAD result. Actual required checks or explicit exact-revision acceptance still apply.
- For behavior-neutral documentation/comments, run only relevant format, link, command or documentation-contract checks. Instruction edits also require review for ambiguity, duplication, conflicts, authorization and completion boundaries. Do not run unrelated strategy or economic tests merely for documentation. Executable configuration, generated inputs and parsed documentation are not automatically behavior-neutral.
- For changes affecting money, orders, risk, security or persistent data, verify the affected invariants and necessary integration/replay paths. Run expensive/full validation on a stable candidate only when the impact or applicable delivery contract requires it. Do not weaken safety checks, frozen thresholds, fixtures, data integrity or evidence retention to pass tests.
- Review the task diff once; repeat focused review after material changes. Reuse existing tests and logs rather than building a new validation framework. Report what was verified, reused, not run or failed, with its scope; a partial pass is not full acceptance. Do not fabricate evidence, hide failures or bypass branch protection and required reviews/checks.

## Execution and delivery

Continue safe authorized work without repeated requests to continue. Resolve factual ambiguity by reading; ask only for a necessary decision that cannot be resolved safely. Authorization does not imply spending, live trading, credential/permission changes, irreversible actions or unrelated external writes. Do not change scheduled tasks without explicit scheduling authorization.

Resume the matching branch/PR; new work uses a feature branch unless a direct default-branch update is explicitly authorized. Preserve any PR-only policy. Save coherent milestones, push authorized changes and verify the remote SHA. Reuse the existing PR/recovery entry; do not create empty bootstrap commits, temporary process files or routine Issues. Without explicit authorization, do not reset, clean, rebase, force-push, rewrite history, delete branches/worktrees, discard unknown work or overwrite unrelated changes. Never commit secrets.

A failed check or candidate calls for diagnosis and an evidence-supported correction or bounded alternative, not automatic task termination or repetitive trials. Stay within scope and budget, preserve failures, and continue independent work past local blockers. Finish when applicable acceptance and actual required checks are satisfied; do not add marginal optimization afterward. A checkpoint or PR alone is not completion. When no safe authorized action remains, preserve recoverable progress and report completed, failed, blocked and unverified items without promising background completion.

## trade entry points and boundaries

When architecture or commands are needed, consult `.github/PROJECT_BRIEF.md`, `README.md`, `docs/ARCHITECTURE.md`, `docs/VALIDATION.md`, `tests/` and `.github/workflows/ci.yml` for the affected contract. `quantfusion/` is the sole implementation; scripts run as modules rather than root-level Python APIs.

This is daily-bar research and manual decision support, not broker automation. Preserve close-to-next-tradable-open causality, account/risk state across routing, fail-closed inputs and transactional publication. Diagnostic stress subsets are not canonical acceptance evidence. Do not change frozen risk thresholds, scenarios, metrics, data or evidence identities merely to obtain passing results; economic changes require the current task's explicit scope and applicable acceptance.

## Git/GitHub transfer and preservation

- Inspect object identities, sizes and outgoing paths before transfers; select necessary files, reuse unchanged references, and never indiscriminately upload working directories. Prefer authorized native Git or file-aware programmatic transfer; when unavailable, use the authorized connector without extracting its credentials. Do not repeat a confirmed-failed transport.
- Keep large payloads out of model/tool text and arguments: no complete Base64, huge JSON, archives, full logs or chunk-then-giant-request uploads. Prefer file-to-file, selective/range reads and bounded excerpts. String-only connectors are for small recoverable batches.
- Required large originals still require preservation. Use supported resumable or deterministic multipart transport when necessary, keeping order, offsets, raw/encoded lengths and hashes; verify byte-for-byte reconstruction and the expected Git/LFS object identity where applicable. Separate blobs are not append operations. A summary/hash is not a backup.
- Keep large transfers bounded and serial. Reuse a concise ledger of local/remote locations, identities and verified status; inspect state after interruption before retrying. Verify final local bytes and remote tree/commit/ref or storage manifest, not merely a created blob. Report unpreserved originals and temporary-runtime loss risk, while continuing independent work. Never replace required evidence with summaries or rewrite historical evidence.
